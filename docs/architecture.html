Architecture overview

Nirmata Runtime for Kyverno

Kyverno-style CEL policy, enforced in the kernel. A per-node daemon attaches eBPF programs to the pods a RuntimePolicy selects, so a denied file open, exec, or network connection never completes — and a permitted one still shows up as a finding.

Admission checks the spec. Nothing checks the behavior.

A signed image and a validated pod spec say nothing about what the running process then does with them. A clean admission record and a compromised process produce the same audit trail.

Before the pod starts

  • Which image, which labels, which privileges
  • A verdict on what the workload declares
  • Already solved — that's Kyverno at admission

After the pod starts — unwatched until now

  • The files the process opens
  • The binaries it executes
  • The destinations and protocols it uses
  • The names it resolves
Nirmata Runtime is the layer that watches the right-hand column — decided in the kernel, on the pod's own cgroup, without asking the workload to cooperate.

How a policy becomes a kernel decision

One daemon per node watches two informers — RuntimePolicy and its own node's pods — compiles CEL into allow/deny sets, and programs them into eBPF maps read by hooks already attached to each pod's cgroup.

enforce path — kernel returns -EPERM or drops the packet observation path — counted, attributed, matched in userspace

Five behaviors, one policy object

Each RuntimePolicy behavior sets an allow and/or deny list — literal values, a CEL expression, or both, unioned. deny.values: ["*"] flips a behavior from allow-all to deny-all-except-allowed.

open

File paths a process reads. Matched against a per-cgroup map at file_open.

enforce or observe
exec

Binary paths a process launches. Matched at bprm_check_security.

enforce or observe
network

IPv4 addresses, CIDRs, domains, and cluster Service names. Decided at connect time.

enforce or observe
protocol

The application protocol a flow actually speaks, classified from its first data segment — independent of the port it used.

enforce or observe
dns

Hostnames a workload resolves. Reports names outside the declared set.

observe only

Key features

A deliberately narrow CRD, evaluated with the CEL libraries Kyverno already ships, producing output a cluster's existing tooling already reads.

Enforce or monitor, per policy

spec.mode chooses the outcome; the same policy object either blocks a workload or reports on it, so what you learn in monitor mode is exactly what you later enforce.

Readable findings under broad policy

A monitorFilter CEL predicate narrows which monitor-mode observations become a finding, so a wide discovery policy still produces a Report someone will read.

Default deny with allow-lists

deny.values: ["*"] turns any behavior into deny-all-except-allowed, and matching policies union their allow and deny sets across a pod.

CEL-powered, and current

Literal values, CEL expressions, reusable spec.variables, and the Kyverno resource, http, and json libraries; evaluationInterval re-reads external lists without a policy edit.

Kubernetes-native output

OpenReports Report objects per pod, sharded per-node status.nodes with Applied/TargetsValid conditions, and Prometheus counters that distinguish an allowed operation from a blocked one.

Cluster-wide, fail-safe scoping

podSelector and namespaceSelector are ANDed and cluster-scoped; an enforce-mode policy must set one of them explicitly, so blast radius is visible in the policy, not inferred.

Why it matters

The case for a kernel-decided runtime layer, in terms an operator or a security reviewer already reasons in.

Block, not just alert

A denied read, exec, or connection fails in the kernel, at the moment it's attempted. There is no window between detection and response, and no incident to staff for the operations it stops.

Evidence, not inference

Findings carry the attempt, the destination, and the decision, attributed to the pod and container — and the process, for exec/open. An auditor reads an outcome, not a guess about intent.

Nothing to change in the workload

No sidecar, no agent baked into the image, no proxy environment variables, no CA in the trust store, no CNI migration. helm install, and the pod spec is untouched.

The policy stack you already run

An admission-validated CRD and the same Kyverno CEL libraries used elsewhere in the cluster, so review, GitOps, and rollback work exactly as they already do.

Where the layers you already own go blind

Every layer above the kernel decides about traffic the workload chose to send it. A workload that never cooperates — a debug container, an unreviewed sidecar, a compromised process — never reaches most of them.

Adoption path: monitor first, enforce second

One policy object serves both modes, so nothing learned in monitor mode has to be re-expressed to enforce it.

1

Install

helm install the DaemonSet. Egress observation and enforcement need only a cgroup v2 host with BPF support.

2

Observe

Apply a broad monitor-mode policy with a monitorFilter and read the Reports. Every finding is something you would have blocked.

3

Enforce

Narrow podSelector to the workloads that should never do it, then flip the same policy to mode: enforce.

4

Sustain

Drive provider and package lists from a ConfigMap or feed with evaluationInterval, so staying current needs no policy edit.

What this deliberately does not do

Stating the boundary is what makes the claims inside it credible.

Destination scoping
Stays with the CNI. Identity-based L3/L4, FQDN egress, ingress, and encryption are done better there; network targets here are attribution plus static hard denies, not a replacement egress firewall.
Semantic AI enforcement
Stays with the proxy. Which model, which tool, which prompt needs a layer that terminates the connection — a userspace duplicate over undecryptable traffic would be strictly worse.
Ingress
Out of scope. Every hook here is egress or execution, so a pod serving a model, an MCP server, or an agent card is not observed — that belongs to admission control and RBAC on pods/portforward.
Content inside TLS
Not knowable here. Model names, prompts, tool arguments, and HTTP paths require the client's cooperation, which is exactly what a shadow workload withholds.
Current status

Pre-1.0, API v1alpha1. File open and process exec enforcement need a kernel booted with BPF-LSM active (lsm=bpf); egress is keyed on IPv4 destination addresses only, so IPv6 is neither enforced nor observed; network, protocol, open, and exec observations are drained on a poll interval rather than streamed; policy exceptions are not yet supported.
